# Phase 2：真实 AI-Lab 文档语义检索总结

日期：2026-09-05（Asia/Tokyo）

## 实际应用意义

Phase 1 只在 12 个手写短段落中证明了“语义检索成立”。Phase 2 把它变成可实际使用的本地资料搜索工具：已有 AI 实验的 README、设计文档和结果报告会被切成带出处的段落，预先计算向量并保存。以后提问时无需逐文件搜索，也无需重新计算全部资料。

整个建库与查询过程均在本机完成，不调用网络服务，也不把研究文档发送到外部。

## 索引范围

- 来源：AI-Lab 顶层 README、各项目根 README、`docs/**/*.md`、`results/**/*.md`；
- 纳入：68 个 Markdown 文件；
- 切块：487 个段落，每块最多约 1400 字符；
- 每块保存项目名、相对路径、标题层级、起止行号、原文和 1024 维向量；
- 向量输入包含项目名、文件路径、章节标题与正文；
- 排除：第三方源码/worktree、Git 内容、测试和夹具、非 Markdown 日志、模型生成的旧答案、当前 embedding 项目的 `results/`；
- `index/manifest.json` 保存纳入文件的大小和 SHA-256，便于检查索引来源。

## 中日英跨项目评测

使用 8 个没有参与文档写作的自然语言问题，覆盖中文、日文和英文，以及 Wan、Qwen3-VL、Flux、Whisper 与 Qwen3-14B 五个项目。

| 指标 | 结果 |
| --- | ---: |
| 正确项目 Recall@1 | 8/8 |
| 正确项目 Recall@3 | 8/8 |
| 指定首选报告 Recall@3 | 5/8 |
| 8 个查询向量计算 | 0.876 秒 |
| 查询阶段最大常驻内存 | 4,741,054,464 bytes（4.42 GiB） |
| swap | 0 |

8 个问题的第一名全部来自正确项目，包括：

- 中文问题找到猫眨眼未完全成功的 Wan 视频报告；
- 日文问题找到日文票据 OCR 中的 `TP` 与表格结构；
- 英文问题找到绿色杯子比例过大的 Flux 编辑实验；
- 中文问题找到麦克风字幕延迟的 Whisper 实验；
- 日文问题找到 Super TAE 不兼容的根因；
- 英文问题找到 Qwen3-VL 四并发吞吐量与延迟结论。

## 为什么首选报告只有 5/8

这三个结果并非跑到了错误项目，而是同一事实在多份真实资料中重复出现：

- `TP` 同时出现在票据 OCR 的 Phase 7、8、9、10；指定的 Phase 8 排第 5；
- 麦克风字幕延迟同时出现在 Phase 4B、4C、4D；指定的 Phase 4D 排第 7；
- 票据日期的确定性校验在 Phase 8、9、10 和设计文档中都有说明；指定的 Phase 8 排第 7。

向量模型擅长判断“谈的是不是同一件事”，但它不知道人为指定哪一份是权威原始报告。真实 RAG 可先取 top-k，再使用关键词、时间、来源类型或 reranker 做第二次排序。当前版本保留原始向量排名，避免用测试答案硬编码规则。

## 独立使用验收

用评测集之外的问题：

```text
VAE 和 TAE 在视频生成里分别起什么作用？
```

单次检索耗时 0.826 秒。第一名准确找到 Wan 项目总结中的“完整 VAE 与 TAE 的取舍”，并返回原文件第 115–119 行；前五名全部来自相关 Wan 报告。

## 使用方法

资料变化后重建索引：

```bash
scripts/run_phase_2.sh
```

连续提问：

```bash
scripts/search_ai_lab.sh
```

一次性提问：

```bash
scripts/search_ai_lab.sh "为什么猫眨眼只算部分成功？"
```

显示的相似度只用于同一问题下的相对排序，不是答案正确概率。搜索结果仍是原始资料片段，尚未由聊天模型组织成完整答案。

## 结论

Phase 2 已完成：Qwen3-Embedding-0.6B Q8_0 在 M2 Max 上能够用不到一秒的查询向量计算，从 487 个真实中日英混合研究段落中稳定定位正确项目，并给出可核对的文件、章节和行号。它已经是一套可用的离线实验资料搜索入口。

下一阶段如果继续，将是 Phase 3 本地 RAG：检索层只负责找原文，再由本地聊天模型依据这些原文回答并引用来源，同时专门测试“资料中没有答案时是否会承认不知道”。
