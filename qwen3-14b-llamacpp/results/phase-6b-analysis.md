# Phase 6B：KV cache 长上下文质量结论

## 结果

同一份 110 条虚构巡检记录、同一组问题、同一随机种子，在 16K 上下文下得到：

| KV cache | 得分 | 峰值常驻内存 | 完整进程耗时 |
| --- | ---: | ---: | ---: |
| Q4_0 | 7 / 7 | 9.24 GiB | 36.40 s |
| Q8_0 | 7 / 7 | 9.88 GiB | 36.14 s |
| F16 | 7 / 7 | 11.05 GiB | 35.01 s |

三档都正确找到了分散在文档不同位置的五个事实，正确完成跨段加法，也没有编造文档中未提及的屋顶颜色。

## 怎么理解

- 这次任务没有测出 Q4_0、Q8_0 与 F16 的回答质量差异。
- 与 F16 相比，本次 Q8_0 少占约 1.17 GiB，Q4_0 少占约 1.80 GiB。
- 三次完整耗时相差约 1.4 秒。单次运行会受模型缓存、系统调度和测试顺序影响，不能据此断言 F16 一定更快。
- 这里量化的是聊天过程中不断增长的 KV cache，不是把 Qwen3-14B Q4_K_M 模型权重重新量化。

## 建议

日常 16K 聊天先用 **Q8_0**：本次质量与 F16 相同，同时保留约 1.17 GiB 内存余量。需要给更长上下文或其他应用腾出更多内存时，可切到 **Q4_0**；本次精确信息检索同样满分。

本结论只覆盖一份固定、可复现的长文本测试。它说明“这道测试没有发现损失”，不代表 Q4_0 在所有写作、代码、复杂推理和更长上下文中都与 F16 完全等价。

原始答案、日志和自动评分分别保存在 `results/kv-quality-*.json`、`results/kv-quality-*-latest.log` 和 `results/kv-quality-scores.csv`。
